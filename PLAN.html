Retail Operations Copilot plan

The copilot takes a free-text store issue and returns category, priority, confidence, a cited answer, the data it used, an escalation decision and PII status. The guide requires at least two cooperating agents (M10), so the agents below are each a real, separable step. Keep the deterministic parts (masking, priority overrides, escalation routing, CSV analytics) in code and use the LLM for classification, phrasing and the final answer.

Pipeline

issue text → Safety agent regex PII/card masking, injection and restricted-data detection (code first, LLM second) → Triage agent category + priority + confidence, then rule overrides from SOP priority table → Retrieval agent BM25 or embeddings over KB split by "##" heading → cites file.md#section-slug → Data agent pandas tools: stock-out root cause, unresolved incidents (anchor 2026-10-10 12:00 IST), vendor quality, return threshold, short shipments → Workflow agent escalation_matrix.csv lookup → team, SLA, approval; mock ticket JSON written to file → Composer one LLM call: answer from retrieved sections + data findings only → response JSON

Who builds what

Member A · Safety, triage, eval
  • Shared response schema (Pydantic) matching predictions_schema.csv, done in the first 30 minutes
  • Safety agent: phone, card and email masking; injection and restricted-data refusals (PUB-008, PUB-009)
  • Triage agent: LLM classifier with few-shot examples from support_cases.csv plus rule overrides (store-wide outage, safety or injury words → P1)
  • Orchestrator wiring the agents together
  • Eval runner: writes predictions.csv and the metrics table for the 5 target metrics
Member B · Retrieval, workflow, answers
  • Chunk the 5 KB files by heading; slug anchors exactly like the test file (#pos-card-reader-runbook)
  • Retrieval agent with top-k sections and a score threshold; nothing found means a "not in policy" answer
  • Workflow agent: escalation matrix routing, approval rules (refund thresholds), mock ticket, notification and vendor claim payloads (bonus B3)
  • Composer prompt: answer only from supplied sections, ask a follow-up question when store or SKU is missing
Member C · Data agent, UI, dashboard
  • Data agent tools as plain functions over the CSVs: stock-out analysis (inventory + receipts + vendor fill rate + warehouse WH001), incidents in the last 24 hours, vendor complaints in the last 30 days, return lookup
  • Root-cause explanation (bonus B1), e.g. tennis balls: store and warehouse both at zero
  • Streamlit app: Triage tab, Analytics tab, Eval tab showing the metrics table
  • Dashboard (bonus B2): open cases, priority mix, category mix, region trends

Targets and traps

Targets from the guide
  • Category and priority accuracy ≥ 75%
  • Citation presence on policy answers ≥ 85%
  • Safety pass rate 100% on public safety cases
  • Data-use correctness ≥ 75%
Avoid
  • Hard-coding answers for the 11 public prompts. Judges use hidden prompts; build general tools.
  • Letting the LLM do counts or date maths. Pandas computes, the LLM explains.
  • Echoing a card number back in the answer, the ticket or the logs.
  • Agents that are only prompt names. Each agent must own a distinct job you can explain.
Use Case 1 or 2 · one full day · fixed stack

Support agent plan (retail or university)

The guide scores the simplest design that meets the requirements highest. Build one fixed LangGraph workflow, not a multi-agent system, and be ready to explain why: eligibility, refunds and attendance are deterministic, so they are tools, not agents.

Pipeline

POST /ask (identity only from X-Customer-Id / X-Student-Id header) → classify policy | procedure | personal | calc | what-if | out-of-scope (LLM, JSON-validated, retry, fallback) → authorise personal question with no header or someone else's ID → refused (never confirm the record exists) → retrieve ChromaDB top-k with metadata filter: effective on as_of_date, scope matches → resolve Annex A precedence: applicability → supersession → authority → recency → conflict_flagged → tools SQLite lookups + eligibility / refund / warranty / attendance, thresholds read from rule_registry → compose LLM writes answer from evidence + tool output only; answer_type set by code, not by the LLM → audit trace_id, sources, tools with inputs/outputs, rules, conflicts, model, tokens, latency

Who builds what

Member A · Data, rules, precedence
  • Find the documents: at least one versioned conflict, a category or tier rule, a table, a not-yet-effective circular
  • source_register.csv (Annex B)
  • SQLite schema exactly as Annex C, plus the rule registry with every rule linked to a clause
  • Synthetic data kit: verbatim prompts, generator, validator with output, loader script for judges, data card. Cover every listed edge case
  • Precedence resolver as a pure, unit-tested function
Member B · Retrieval, ingestion, eval
  • Parse and chunk with section, page, version and date metadata; ChromaDB persisted to disk
  • POST /ingest: file + metadata, optional new rules into the registry, usable immediately
  • GET /sources, citations, not_found abstention threshold
  • Eval set of 20+ questions in the required mix and the harness for all 6 metrics
  • Compare two configurations (chunk size or top-k or embedding model) and record the numbers
Member C · Orchestration, tools, API
  • FastAPI contract: /ask, /health, /audit/{trace_id}, Pydantic v2 models
  • LangGraph workflow above, MOCK_LLM=true mode from hour one
  • Deterministic tools; state-changing tools re-check eligibility and are idempotent
  • Authorisation, injection handling for documents and order notes, PII-free logs
  • Streamlit UI, Docker Compose (Ollama on host)

Points that decide the score

  • Live ingestion (15 pts). A new circular must change what the refund or eligibility tool returns, with no restart. Tools read thresholds from rule_registry through the same precedence resolver.
  • Citations (20 pts). Judges open the cited page. Store the real page and section number with every chunk.
  • Safety (10 pts). Another person's ID in the message text is ignored; the response must not reveal whether that order or student exists.
  • Disqualifiers. Hard-coded answers, no tools, no evaluation, real personal data, shared code.

Team rules for either use case

  1. Agree the shared schema and function signatures before writing code, then build against stubs so nobody waits on anyone.
  2. Everyone commits under their own Git identity, at least hourly. Judges read the history.
  3. Each member writes evaluation cases for their own component.
  4. Hiring is individual and judges question each person about parts they did not build. In the last hour, each member explains another member's component out loud.
  5. Keep an AI_USAGE.md as you go: which parts an assistant generated and how you verified them.
